# Reproducible architectural illustration pipeline

**Status:** Implemented for the six hamlet residences and any user-created
Design Lab design. No AI image is generated by this repository. The pipeline
produces deterministic references and prompts for an external, optional image
workflow.

## Why this exists

Before this phase, the drawings came from the model but the written prompts were
maintained by hand. That allowed two contradictions:

1. a prompt could describe a balcony, window, storey or material that the model
   did not contain;
2. a design change updated the drawings but left the prompt and reference stale.

The pipeline makes the model the source for the scene, the description, the
prompt, the reference and the package manifest. It also keeps the creative
visualisation text as source material, but corrects it against the data.

## Dependency chain

```
Design JSON (v2.0)
  -> Schema.canonicalize / validate
  -> Illustration configuration (presentation only)
  -> Scene specification (facts + site + camera + constraints + unresolved)
  -> Deterministic schematics / roof plan / reference view
  -> Prompt and negative prompt
  -> Description and manifest
  -> ZIP package
  -> Optional external AI image (not authoritative)
```

Every artifact records the same design hash. A design change invalidates the
affected references and prompts; a presentation change does not invalidate the
floor plans.

## Three kinds of information

| Type | Examples | Mutability |
| --- | --- | --- |
| **Architectural facts** | storeys, module offsets, roof pitch, window position, stair type | From the design model; never changed by the prompt |
| **Architectural intentions** | step-free entrance, adaptable bathroom, green-roof concept | Recorded as intentions, not verified facts |
| **Illustration preferences** | style, season, time, weather, people, camera height | Separate illustration configuration |

The prompt generator labels these separately. It does not promote an intention
to a verified fact.

## Illustration configuration

Schema: `containers-hamlet-illustration/v1`.

```json
{
  "schema": "containers-hamlet-illustration/v1",
  "designId": "hamlet-offset-stack",
  "view": {
    "type": "exterior-three-quarter",
    "camera": { "position": "approach", "height_m": 1.6, "lens_mm": 35 }
  },
  "presentation": {
    "style": "photorealistic",
    "season": "late-summer",
    "time": "late-afternoon",
    "weather": "clear",
    "people": false
  },
  "materialPolicy": "strict-documented"
}
```

Views: `exterior-three-quarter`, `front-approach`, `rear-landscape`,
`elevated-isometric`, `interior-looking-out`, `courtyard-porch`, `room`.

Styles: photorealistic, architectural watercolour, hand-drawn sketch,
presentation rendering, neutral material study, winter visualisation.

Material policies: `strict-documented`, `neutral-unspecified`, `exploratory`.
Exploratory materials are explicitly marked non-authoritative.

## Scene specification

Schema: `containers-hamlet-scene/v1`. The scene is generated by
`site/js/design-illustration.js`.

It contains:

- design identity, revision, schema and design hash;
- camera view, height, lens, world bearing and approximate reference rotation;
- building facts (storeys, modules, types, arrangement, areas, height, roof);
- required module elements with positions, rotations, elevations and support;
- openings, rooms/zones, porches, decks and connections;
- material rows and the documented material passport;
- site identity, principal view, path approach and site rotation;
- constraints (`preserveGeometry`, no additional storeys/openings/outdoor spaces);
- capabilities (exterior reference, container schematic, roof plan, room-zone
  plan; interior perspective is **false**);
- unresolved matters and intentions;
- generated prompt, negative prompt, description and validation.

The scene does not copy the whole design JSON. It references source ids and
records the facts needed for the outputs.

## Site orientation

`site.rotation_deg` converts local bearings to world bearings:
`world = local + site.rotation_deg`. The site's `views.main.azimuth_deg` is the
authoritative principal view. The camera bearing in the prompt is a world
bearing. The design's local south face is not assumed to be geographic south.

The six homes map to their site buildings by `design_lab_home` first, then by
`site.homesite`. This prevents every design from falling back to Cabin A.

## Deterministic drawings

`design-model.js` now also generates:

- **container block plan** — proportional module blocks, storeys, offsets,
  rotations, connections, overall dimensions, legend using line style and hatch
  as well as colour;
- **container block elevation** — ground/upper blocks at explicit elevations;
- **roof plan** — roof outline, ridge/valley, overhang, slope direction and PV
  intent;
- **opposite exterior reference** — axonometric with the camera rotated 180°;
- **approach reference** — orthographic elevation of the entrance facade;
- **site-facing reference** — axonometric rotated so the assigned principal view
  faces the viewer.

All use the same design object. None claims measured perspective.

## Prompt generation

`promptFor(scene)` writes the prompt from the scene, never from hand-written
prose. It includes:

1. design identity and style;
2. storey count and module count;
3. module geometry, rotations, elevations and offsets;
4. roof form, pitch, overhang and PV status;
5. documented openings with face, type, position, size and sill;
6. documented outdoor spaces;
7. site, principal view, path approach and world camera bearing;
8. season, time, weather and people;
9. material policy;
10. explicit restrictions;
11. unresolved matters;
12. the fact that the result is an interpretation, not a construction drawing.

The negative prompt separates geometric contradictions, architectural
additions, rendering artifacts, environmental contradictions and safety-related
visual errors.

## Consistency checks

`validateScene(scene, design)` compares the scene against the model:

- design id and hash;
- storey count, module count and roof type/pitch;
- every module id and every opening;
- constraints that forbid additional geometry;
- interior perspective capability;
- warnings for people, exploratory materials or an unmodeled interior claim.

Tests validate the structured scene, not arbitrary English. Prompt text is
generated from those structured facts.

## Freshness and manifests

`designHash` covers the canonical architectural model, excluding derived
assessment and export metadata. `presentationHash` covers the illustration
configuration. The editor stores the hash used for the current prompt/reference
and marks them **outdated** when the design changes.

A package manifest records:

- design id, revision, schema version and design hash;
- scene hash and presentation hash;
- generator version and generation date;
- the seven files that are actually published in the package (`artifacts`);
- the shared drawings and references under `/design-lab/views/`
  (`sharedArtifacts`), with relative paths, types, dependencies and hashes;
- known limitations.

The published manifest is not the same as the editor ZIP plan. The editor ZIP
uses virtual paths (`prompts/exterior.md`, `drawings/…`, `references/…`) because
it really contains those files. The published package writes `prompt.md`,
`interior.md`, `negative.md`, `config.json` and `scene.json` and links to the
shared views, so its manifest must not claim files that are not there.

The editor's **Download package ZIP** includes the design, description, scene,
prompt, negative prompt, configuration, drawings, reference and manifest.

## Interior illustration readiness

The Phase 3 interior model adds room polygons, partitions, doors, fixtures and
clearances to the scene. Capabilities are explicit:

- exterior reference available;
- interior zone diagram available;
- detailed interior floor plan available when room polygons exist;
- interior illustration prompt available when rooms exist;
- spatially accurate interior perspective **unavailable** — no interior camera
  or perspective renderer is implemented.

Room polygons and fixtures can support a richer prompt without supporting a
geometrically accurate perspective. The generated interior prompt uses room
areas, module references, partitions, door connections, fixtures and unresolved
items. It states the camera limitation and does not invent windows or furniture.

Interior changes invalidate the design hash and dependent interior drawings,
scenes and prompts. Presentation-only changes do not alter the design hash.

## Editor

The **Illustrate** section of `/design-lab/editor/` provides:

- viewpoint, camera height/lens, style, season, time, weather, people and
  material policy;
- a deterministic reference view;
- a generated prompt and negative prompt;
- facts, intentions and unresolved matters;
- copy, download prompt, download config and download package ZIP;
- current/outdated status with a regeneration control.

It uses native controls and keyboard activation. It does not require a backend,
account, API key or network request.

## Six-home packages

`/design-lab/illustration/` publishes a package for each hamlet residence:
prompt, interior prompt, negative prompt, description, configuration, scene and
manifest. The drawings and references are shared from the same generated model
and listed as `sharedArtifacts` in the manifest.

The build does not duplicate all drawings into every package; the editor ZIP
does so for portability.

## Accessibility

- SVG outputs have `role="img"`, `<title>` and `<desc>`.
- Dimensions and facts are repeated in text/tables, not only inside the SVG.
- The prompt and negative prompt are keyboard-focusable regions with labels.
- The editor uses native labelled controls and a polite status.
- No geometry is drag-only; numeric and keyboard controls remain.
- The public illustration page has no autoplay, no animation and no dark
  patterns.
- Automated axe checks are not a claim of complete accessibility conformance.

## Known limits

- Interior perspective is unavailable: no interior camera or perspective
  renderer exists. Room polygons and fixtures support a detailed prompt and
  plan, but the pipeline refuses to claim a spatially accurate interior view.
- Reference views are approximate SVG projections, not measured photographs.
- The prompt is a structured interpretation; the external image can still add or
  remove detail. It must not be treated as a drawing.
- No AI image generation, no image verification, no structural/energy/code
  analysis.
- No PNG reference export in this phase; SVG is the canonical reference.
- No BIM/IFC or 3D site model.

## Solar-aware scene facts

For a residence with a canonical energy model, `sceneSpec` now includes a
`solar` object: exact installed panel count, capacity, panel area, visible panel
count for the camera bearing, per-array count/rows/columns/tilt/azimuth/
mounting/surface/electrical group, panel dimensions, canopy dimensions,
maintenance access and snow-shedding. The prompt states the exact count and
forbids adding, removing, merging or rearranging panels. A viewpoint that cannot
see the south array reports zero visible panels rather than inventing them. The
scene validates that the count matches the canonical geometry. Generated images
that deviate remain discrepancies; the geometric model is authoritative.
